# AI Jobs Pipeline v2 — Server-side progress & strict contract

**Дата:** 02.02.2026

---

## 1. Цель и проблема (до / после)

### До начала работ

- `AIJob.status` использовался как единственный источник истины
- Отсутствовало понимание:
  - на каком этапе находится job
  - что именно делает backend
  - почему job может «зависнуть»
- Frontend не мог:
  - показывать прогресс
  - объяснять пользователю, что происходит
- Ошибки хранились несистемно:
  - частично структурировано
  - частично строкой в `error`

### Цель изменений

Перейти от разрозненных статусов к **управляемому, наблюдаемому AI-пайплайну**, где:

- backend является единственным источником истины
- frontend только читает состояние
- каждый этап выполнения явно зафиксирован
- прогресс нормализован
- ошибки диагностируемы

---

## 2. Архитектурное решение: разделение понятий

Мы осознанно разделили ответственность между сущностями:

| Сущность | Назначение |
|--------|------------|
| `status` | legacy-состояние (совместимость, derived) |
| `stage` | реальный pipeline выполнения |
| `progress` | нормализованный процент (0–100) |
| `stage_message` | человеко-читаемое описание для UI |

**Ключевой принцип:**

> `status` больше не источник истины, а производное от `stage`.

---

## 3. Контракт этапов AIJobStage

`AIJobStage` — это **жёсткий backend → frontend контракт**.

### Зафиксированный порядок этапов

1. `queued`
2. `analyze_request`
3. `ai_processing`
4. `ai_response_received`
5. `product_create`
6. `state_transition`
7. `done`
8. `failed`

### Правила контракта

- порядок этапов фиксирован
- этапы нельзя пропускать
- frontend **никогда** не пишет `stage`
- backend пишет только значения enum
- произвольные строки запрещены

---

## 4. Модель AIJob (apps/api/models.py)

### Добавленные поля

- `stage: String` — текущий этап pipeline
- `progress: Integer` — прогресс 0–100
- `stage_message: Text` — описание для UI

### Гарантии на уровне БД

- `CheckConstraint` запрещает невалидные значения `stage`
- добавлены индексы:
  - `ix_ai_jobs_status`
  - `ix_ai_jobs_stage`

Это гарантирует:

- отсутствие «мусорных» состояний
- предсказуемые выборки
- безопасность при масштабировании

---

## 5. Управление состоянием: set_stage и _apply_stage

### AIJob.set_stage(...)

Централизует:

- смену `stage`
- установку `stage_message`
- синхронизацию legacy `status`

**Запрещено:**

- писать `job.stage = ...` напрямую
- писать `job.status = ...` вне этой логики

---

### _apply_stage(job, stage, message)

Единая точка управления переходами:

- вызывает `set_stage`
- выставляет нормализованный `progress`
- гарантирует консистентность состояния

Все переходы pipeline проходят **только через неё**.

---

## 6. Pipeline выполнения (apps/api/jobs.py)

Логика `process_ai_job()` переписана под сценарный pipeline:

1. `ANALYZE_REQUEST` — подготовка запроса
2. `AI_PROCESSING` — запрос в AI
3. `AI_RESPONSE_RECEIVED` — ответ получен
4. `PRODUCT_CREATE` — создание сущностей
5. `STATE_TRANSITION` — бизнес-логика
6. `DONE` / `FAILED`

Каждый этап:

- фиксируется в БД
- имеет `stage_message`
- имеет нормализованный `progress`

Код читается как сценарий, а не набор разрозненных условий.

---

## 7. Нормализация прогресса

Единый источник истины:

```
STAGE_PROGRESS = {
    QUEUED: 0,
    ANALYZE_REQUEST: 10,
    AI_PROCESSING: 30,
    AI_RESPONSE_RECEIVED: 60,
    PRODUCT_CREATE: 80,
    STATE_TRANSITION: 90,
    DONE: 100,
    FAILED: 100,
}
```

Преимущества:

- frontend получает предсказуемый процент
- backend не «угадывает» прогресс
- легко менять веса этапов

---

## 8. Ошибки и диагностика

`_fail_job()` гарантирует:

- всегда выставляется `FAILED`
- фиксируются:
  - `error_stage`
  - `error_code`
  - `error_message`
- job не остаётся в промежуточном состоянии

Ошибки становятся анализируемыми по этапам.

---

## 9. Что намеренно НЕ делали

Осознанные ограничения:

- ❌ не ломали существующие данные
- ❌ не удаляли `status`
- ❌ не трогали очередь / Redis / RQ
- ❌ не меняли API-контракты

Это эволюция архитектуры, а не разрушительный рефакторинг.

---

## 10. Гарантии и инварианты

Система гарантирует:

- backend полностью управляет pipeline
- frontend является «тонким» читателем состояния
- каждый AI job наблюдаем
- состояние job всегда консистентно

---

## 11. Как расширять pipeline дальше

Допустимо:

- добавлять новые этапы **в конец или между существующими**,
  при обновлении enum и `STAGE_PROGRESS`
- добавлять новые `stage_message`

Запрещено:

- менять порядок существующих этапов
- удалять этапы без миграции

---

## 12. Связь с frontend и API

Frontend:

- читает `stage`, `progress`, `stage_message`
- не интерпретирует `status`

Backend:

- управляет состоянием
- гарантирует контракт

AI-пайплайн стал:

> наблюдаемым, объяснимым и масштабируемым
