**Дата:** 01-02-2026
**Проект:** clothing-site
**Назначение:** регламент подготовки, запуска и сопровождения integration-тестирования backend-системы

## 1. Цель документа

Данный документ фиксирует:

* архитектурные решения по тестированию,
* изменения, внесённые в инфраструктуру,
* принципы написания integration-тестов,
* порядок запуска и проверки,
* правила масштабирования тестового контура.

Документ является **базовой версией (v1)** и используется как:

* внутренняя техническая документация,
* основа для CI/CD,
* onboarding-гайд для разработчиков.

---

## 2. Контекст и предпосылки

Проект `clothing-site` представляет собой микросервисную backend-систему, включающую:

* API (FastAPI)
* AI-сервис
* Worker (RQ)
* PostgreSQL
* Redis
* MinIO (S3)
* Meilisearch

Для корректного тестирования бизнес-логики требуется **реальное окружение**, максимально приближенное к production, без mock-сервисов.

---

## 3. Выбранная стратегия тестирования

### Ключевое решение

Используется **integration-first подход**.

### Почему

* бизнес-логика распределена между сервисами;
* важны side-effects (БД, S3, индексы);
* unit-тесты не выявляют проблем интеграции.

---

## 4. Принципиальные ограничения

* ❌ не используются mock-версии DB / Redis / MinIO
* ❌ не используются sleep / timeouts в тестах
* ❌ тесты не зависят друг от друга
* ✅ тесты проверяют реальные контракты
* ✅ каждый тест воспроизводим

---

## 5. Архитектура тестового окружения

Тестовое окружение поднимается **через Docker Compose** и включает:

* отдельную БД (`clothing_test`)
* отдельные очереди Redis
* отдельный S3-bucket
* отдельный Meilisearch-index

Окружение полностью изолировано от production.

---

## 6. Основной инфраструктурный файл

**compose.test.yaml** — ключевой файл тестового контура.

Он отвечает за:

* запуск всех сервисов,
* порядок их инициализации,
* health-checks,
* подготовку S3 (через init-контейнер).

---

## 7. Роль сервиса minio-init

Добавлен отдельный сервис `minio-init`.

### Назначение

* гарантированно создать bucket `products-test`
* избежать `AccessDenied` при старте API / AI
* исключить race condition при запуске

### Принцип

`minio-init`:

* запускается **один раз**
* завершает работу (`Exited`)
* используется как dependency (`service_completed_successfully`)

---

## 8. Порядок инициализации сервисов

1. PostgreSQL (healthcheck)
2. Redis (healthcheck)
3. MinIO
4. **MinIO-init**
5. Meilisearch (healthcheck)
6. AI
7. API
8. Worker

Этот порядок зафиксирован через `depends_on`.

---

## 9. Принцип health-checks

Каждый критичный сервис обязан иметь health-check:

| Сервис      | Тип              |
| ----------- | ---------------- |
| PostgreSQL  | pg_isready       |
| Redis       | redis-cli ping   |
| Meilisearch | HTTP /health     |
| API         | /health endpoint |

## 11. Принцип соответствия структуре приложения

> Структура тестов **зеркалирует архитектуру сервисов**

* `tests/integration/api` → API
* `tests/integration/ai` → AI
* `tests/integration/worker` → Worker

Это упрощает поддержку и масштабирование.

---

## 12. Типы тестов

### API integration tests

Проверяют:

* HTTP-контракты
* side-effects
* сериализацию

### AI integration tests

Проверяют:

* входные данные
* создание job
* финальные статусы

### Worker tests

Проверяют:

* выполнение задач
* изменение статусов
* появление результатов

---

## 13. Структура одного integration-теста

Каждый тест следует шаблону:

1. **Given** — подготовка данных
2. **When** — вызов API
3. **Then** — проверка ответа
4. **And** — проверка side-effects

---

## 14. conftest.py

`conftest.py` отвечает за:

* HTTP client
* base URL (`http://localhost:8101`)
* общие фикстуры
* очистку тестовых данных

Он **не управляет Docker**.

---

## 15. pytest.ini

```ini
[pytest]
testpaths = tests
markers =
    integration: integration tests
    slow: long-running tests
addopts = -ra -q
```

---

## 16. Маркировка тестов

Каждый integration-тест обязан иметь маркер:

```python
@pytest.mark.integration
```

Это позволяет гибко управлять запуском.

---

## 17. Подготовка окружения для тестирования

```bash
docker compose -f compose.test.yaml down --remove-orphans
docker compose -f compose.test.yaml build
docker compose -f compose.test.yaml up -d
```

---

## 18. Проверка готовности API

```bash
curl http://localhost:8101/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

---

## 19. Запуск тестов

### Только integration-тесты

```bash
pytest -m integration
```

### Все тесты

```bash
pytest
```

---

## 20. Работа с данными в тестах

Используются:

* уникальные идентификаторы
* временные сущности
* локальный cleanup

**Полный reset БД не применяется.**

---

## 21. Поведение при ошибках

При падении тестов:

1. Docker **не перезапускается**
2. Анализируются логи сервисов
3. Исправляется причина, а не симптом

---

## 22. Готовность к CI/CD

Контур готов к автоматизации:

```text
CI:
- docker compose up
- wait for /health
- pytest
- docker compose down
```
